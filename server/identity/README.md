# ADR-002 identity service

This Axum crate is the first server application component. It implements invite-gated account creation, login, rotating refresh credentials, logout, `GET /v1/me`, admin-issued invitations, and host-only first-admin bootstrap and credential recovery. The standalone ADR-002 API is deployed on the Azure test VM with disposable `test-admin` and regular `test-user` accounts in the `Cordel-Test` community. Local ADR-003 source adds community and channel routes, moderation, a reusable authorization policy, and host-only admin role changes; it is not deployed. Local ADR-004 source adds transactional chat sends, per-channel sequence allocation, idempotent retries, paginated history, authenticated live `GET /v1/events` delivery, and the native client live session; it is source-Done but not deployed. Server ADR-009 must add browser cookies and CSRF. No public admin recovery, public community creation, or email reset route exists.

The source now implements a short-lived, session-bound admin grant obtained by re-entering the account's own password. The invitation route requires that grant; an ordinary admin app access token is rejected. On the Azure VM, migration `2`, runtime grants, and the new API binary are installed. The guarded local route probe passed. The row-lock privilege repair and focused disposable-admin invitation checks passed. Do not admit real users until the remaining deployment and product gates pass. See the [upgrade handoff](../../deploy/native/admin-grant-upgrade-handoff.md).

## Runtime inputs

- `DATABASE_URL`: PostgreSQL connection URL for a dedicated Cordel database. Run the separate `migrate` command with a migration role before bootstrap or service startup. The `serve` command does not need schema-changing privileges; use a narrower runtime role for it.
- `CORDEL_JWT_SECRET_HEX`: at least 64 hexadecimal characters representing 32 random bytes. Generate with `openssl rand -hex 32`; store in a root-controlled host secret file and inject through systemd. Never commit or print the value. Rotating it invalidates access tokens, while database-backed refresh credentials continue until revoked or expired.
- `CORDEL_LISTEN_ADDR`: optional loopback address, default `127.0.0.1:3000`. The binary refuses a non-loopback bind. The Azure Caddy configuration routes `/v1/*` to Axum and other paths to LiveKit; the API is exposed only through HTTPS.

Build from this directory with `cargo build --locked`. The lockfile was generated and tested in isolated Azure Cloud Shell on 2026-10-18. Apply the schema once with `cargo run --locked -- migrate` using an operator database role; then start `cargo run --locked -- serve` with a restricted runtime role in a disposable environment. The CLI migration and server should not run against a production database as an informal test.

The host-only commands prompt for the password without placing it in process arguments:

```bash
cargo run -- bootstrap-admin admin "Test Community"
cargo run -- recover-admin admin
cargo run -- grant-admin existing-user
cargo run -- revoke-admin existing-admin
```

Run those only through authorized host access. `bootstrap-admin` refuses a second community. `recover-admin` changes an existing admin password, revokes that account's sessions, and writes an audit row. The role commands reject moderated promotion and removal of the last active admin. All commands write `host_audit` with the OS operator name; the host access log is the authoritative proof of who ran them. Avoid shell history, HTTP, and chat for credentials.

ADR-003 migration `3` and its routes remain local. Apply [runtime-grants-003.sql](runtime-grants-003.sql) with the PostgreSQL operator role after migration and before switching the binary. It grants only the new channel, audit, community, and membership privileges the restricted API role needs. Existing session and grant privileges remain necessary. Build and migration deployment require a separate host change; a successful source check is not a VM deployment.

ADR-004 migration `4` adds `channels.last_seq` and the `messages` table. Apply [runtime-grants-004.sql](runtime-grants-004.sql) after migration and before switching the binary; it grants `SELECT, INSERT` on `messages` and `UPDATE (last_seq)` on `channels`, without rewrite or delete rights. `POST /v1/channels/{channel_id}/messages` assigns the next sequence and stores the message in one transaction, and returns the original acknowledgement when the same author retries the same `client_message_id`. `client_message_id` is 1–128 UTF-8 bytes and `body` is 1–4000 UTF-8 bytes. `GET` supports `after_seq`, `before_seq`, `limit`, and `has_more`.

`GET /v1/events` upgrades to a WebSocket after authenticating the native access token in the upgrade header. The server sends `ready`, accepts `subscribe` and `unsubscribe` for text channels, replies with `subscribed` (including the current `last_seq`), `unsubscribed`, or a stable error, and forwards committed messages after the send transaction. Delivery is best effort: every event is forwarded, the client buffers during history catch-up and deduplicates by `(channel_id, seq)`, and a slow receiver gets `lagged` frames prompting `after_seq` recovery. Each delivery and a 30-second heartbeat re-check the session and membership state; a kick, ban, logout, or session expiry sends `access_revoked` with the current `authorization_revision` and closes the socket. The in-process broadcast bus is single-host. The native client live session, WSS/HTTPS transports, and native fixtures are in `client/state` and `docs/contracts/fixtures/native/`; browser admission, multi-instance fan-out, presence, and rich content remain separate ADRs.

## Media admission

`POST /v1/voice-channels/{channel_id}/admission` issues one LiveKit JWT for one account and one voice channel. The room name is `voice:<channel-uuid>:<generation>`, and the generation is the community's `authorization_revision`, which already advances on a kick or a ban. The token may join, publish, and subscribe, and it may not publish data tracks, create rooms, or administer them, so chat cannot ride a LiveKit data track. It lives 300 seconds, which matches the app access token; LiveKit checks it when a participant joins, not during a call.

`CORDEL_LIVEKIT_API_KEY`, `CORDEL_LIVEKIT_API_SECRET`, and `CORDEL_LIVEKIT_URL` are optional and must be set together. Without them the media routes are not registered, so an identity-only deployment is unchanged. The API secret needs at least 32 characters, the same rule LiveKit applies, and the server refuses to start with a shorter one.

`POST /v1/livekit/webhook` verifies the JWT in the `Authorization` header with the API secret, compares the `sha256` claim with the digest of the raw body, checks the issuer, and ignores a repeated event id. It records an ephemeral observation and never grants access. The durable presence snapshot and the reconciliation after a restart belong to Server 010.

## Media admission gate and drain

A second loopback listener, `CORDEL_MEDIA_GATE_ADDR` (default `127.0.0.1:3001`), carries `GET /v1/livekit/authorize`. The reverse proxy calls it before it proxies the LiveKit signaling upgrade, and a non-2xx answer keeps the client out of the room. The route is not on the public `/v1/*` path.

The gate refuses a token unless its signature, issuer, and expiry are valid, the room names a known voice channel, the generation equals the community's current `authorization_revision`, the account is an active member, and the app session named in the token is still live. The token arrives in the `X-Cordel-Livekit-Token` header, so it does not land in the gate's access log.

A moderation action deletes the rooms of the previous generation through the LiveKit server API, which disconnects everyone in them so the members rejoin in the current room. `CORDEL_LIVEKIT_API_URL` points at the host-local server API; without it the moderation response reports `media_drained: false`, because the action is not fully applied while a moderated account is still in a room.

## Contract and limits

The routes follow [v1.md](../../docs/contracts/v1.md). HTTP errors use the v1 JSON envelope. `POST /v1/accounts` explicitly returns `public_registration_disabled`; only `POST /v1/accounts/from-invite` creates a public account. A native client sends its app access token in `Authorization: Bearer ...`. `POST /v1/sessions/admin-grant` checks the current admin role and the account's own password, then issues a random grant for 600 seconds. `DELETE /v1/sessions/admin-grant` revokes it. Management routes require the grant as their bearer. Only its SHA-256 hash is stored. Browser cookie admission is not implemented here.

Logins are 3–32 ASCII letters, digits, `_` or `-`, unique without case. Passwords are 12–128 UTF-8 bytes. Invitations default to 24 hours and one use; an admin may request 1–168 hours and 1–25 uses. Invite codes are 32 random bytes rendered as hexadecimal; only a SHA-256 digest is stored. An unknown, expired, exhausted, or login-colliding redemption returns the same public `invalid_input` response. Login failures return `unauthenticated` without revealing account existence. The in-process rate limiter allows 10 login attempts per normalized login, 100 invite redemption attempts, and 300 refresh attempts per 10 minutes, with a 600-attempt global ceiling. It resets on restart and is a first-test abuse bound, not a distributed rate limiter.

App access JWTs expire after five minutes. A refresh session expires after 30 days. Each refresh consumes its old credential and inserts a new hash in one transaction. Replaying a consumed credential revokes the session family immediately. There is no retry grace: if the refresh response is lost, a client should return to login rather than retry the old credential. Logout revokes the current session; host recovery revokes every session for that admin. `GET /v1/me` checks current membership moderation fields and session status in PostgreSQL on every request. Other server ADRs must use the same authoritative check; a valid JWT alone is insufficient.

The session and invite response types redact credentials from their Rust `Debug` implementation. Do not log raw request/response bodies, Authorization headers, access tokens, refresh tokens, invite codes, or database connection URLs. The fixed [identity fixtures](../../docs/contracts/fixtures/v1/) contain only unusable test values.

Run `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test` here when a Rust toolchain is available. To run the database scenario, first create a **disposable** PostgreSQL database with a name beginning `cordel_identity_test_`, give the test role ownership, and set `CORDEL_TEST_DATABASE_URL` to that database. Then run:

```bash
cargo test disposable_database_identity_flow -- --ignored --nocapture
cargo test disposable_database_community_flow -- --ignored --nocapture
cargo test disposable_database_chat_flow -- --ignored --nocapture
cargo test disposable_database_websocket_flow -- --ignored --nocapture
```

The test asserts the database-name prefix before truncating its identity tables. It covers first-admin bootstrap refusal on repeat, denial of an ordinary admin token at the invitation route, password unlock, demotion and explicit lock, concurrent single-use redemption, expired and colliding redemption, refresh rotation/reuse revocation, logout, recovery, and stored hash/audit properties. The chat flow additionally covers idempotent retries, conflicting reuse, voice-channel rejection, ascending and descending pages, eight concurrent sends with contiguous sequences, and logout revocation. The WebSocket flow binds a real loopback listener and covers an unauthenticated upgrade rejection, `ready`, voice-channel subscription rejection, text subscriptions, live sequences, no duplicate event on an idempotent REST retry, out-of-order forwarding, unsubscribe, resubscribe `last_seq`, `v=99` rejection with `unsupported_version`, a clean disconnect that left zero broadcast receivers followed by a committed message recovered through `after_seq` history, and ban-triggered `access_revoked` without a later protected message. The ignored `disposable_database_native_client_flow` additionally drives the real `client/state` `LiveSession` and native WSS/HTTPS transports against the loopback router through subscribe, stable-id send, live delivery, an offline commit, and reconnect catch-up.
