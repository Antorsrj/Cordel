# Cordel v1 application contract

**Status:** implementation baseline for Accepted ADRs; browser cookie admission, media revocation, image storage, and E2EE sections remain gated by their Proposed ADRs.

This file is the common input for independent server and client workstreams. It defines the first contract shape; it is not a claim that any endpoint exists. When implementation evidence requires a breaking change, update this file and the affected ADRs in the same reviewed change before changing either side. The [workstream map](../adr/WORKSTREAMS.md) names the owner and consumers of each seam.

## Encoding and compatibility

- Public app calls use HTTPS; live app events use WSS. JSON uses UTF-8 and `snake_case` field names. All timestamps are UTC RFC 3339 strings. IDs are opaque UUID strings; clients do not infer order or permissions from IDs.
- Every JSON response or event includes `schema_version: 1`. Additive optional fields are allowed within v1. Receivers ignore unknown fields and unknown event types. Removing a field, changing its meaning, or changing an error category needs a new schema version and a migration plan.
- Sequence numbers and snapshot revisions are unsigned decimal **strings** in JSON so browsers do not lose integer precision. They are compared numerically, never lexically. Chat sequence is per channel. Presence revision is per community and is not a chat sequence.
- A non-2xx REST response has `{ "schema_version": 1, "error": { "code": "...", "message": "..." } }`. `message` is safe to display but is not a stable programmatic key. Stable codes include `unauthenticated`, `forbidden`, `not_found`, `conflict`, `expired`, `rate_limited`, `invalid_input`, `payload_too_large`, and `temporarily_unavailable`. Do not expose whether a login or invite exists through distinguishable public errors.
- Server configuration owns numeric rate, body, upload, and retention limits. The server returns its effective limit in a validation error where safe. Clients must not assume a documentation example is an unlimited quota.

## Identity and authorization

Native clients send `Authorization: Bearer <app_access_token>` over HTTPS and in the WebSocket upgrade header. The access token is short-lived. The rotating refresh credential is stored only in the OS credential store. The browser path in ADR-009 uses a same-origin `Secure`, `HttpOnly`, `SameSite=Strict` cookie plus CSRF for state-changing requests; it does not place a durable token in a URL or browser JavaScript storage. Browser cookie admission is Proposed until its security gate passes.

Version one has one community but every community-scoped resource contains `community_id`. `user` and `admin` are the only app roles. The host-only admin command has no public endpoint. An admin cannot kick or ban another admin. A kick ends no sooner than 30 minutes after application; a ban has no expiry until an admin lifts it. Every protected read, write, WS subscription, image fetch, and media admission rechecks current membership and moderation state.

### Minimum resource shapes

`GET /v1/me` returns `user_id`, `login`, `community_id`, `role`, and `session_expires_at`. A channel has `channel_id`, `community_id`, `kind` (`text` or `voice`), `name`, and `created_at`. A moderation response states `member_id`, `state` (`active`, `kicked`, or `banned`), `kicked_until` when applicable, and a new `authorization_revision`. Other endpoints that change access return that revision so consumers can discard stale permissions.

`GET /v1/channels/{channel_id}/messages?after_seq=<decimal>&limit=<positive integer>` returns ascending messages plus `has_more`. An omitted cursor requests the most recent page; an explicit cursor requests only messages with greater `seq`. Never accept a cursor as proof of access. `POST` takes a client-generated stable `client_message_id` and v1 content. Retrying with the same ID, author, and channel returns the same committed message; reusing the ID for different content fails with `conflict`.

```json
{
  "schema_version": 1,
  "message_id": "418ab662-4882-43bb-9eaf-5ad43261d6a7",
  "client_message_id": "567e491b-4c30-47ec-9fc0-6744c12a6e87",
  "channel_id": "7efc7a7b-b06f-4632-8780-bb611b8cd0a8",
  "author_id": "6daa8a59-0ac7-4737-bdad-768d60607767",
  "seq": "42",
  "created_at": "2026-10-17T12:00:00Z",
  "content": { "format": "cordel_rich_v1", "blocks": [{ "type": "paragraph", "spans": [{ "text": "Hello", "marks": ["bold"] }] }] },
  "images": []
}
```

The content proposal in ADR-011 allows paragraph spans with `bold`, `italic`, or `code` marks; ordered/unordered lists of span arrays; code blocks as text; and safe links with an explicit HTTPS URL. The server rejects raw HTML, unsupported nodes, invalid nesting, and oversized content. An image appears as an attachment reference in `images`, with `image_id`, `alt_text`, `width`, and `height`; the client obtains protected bytes through the image endpoint. The exact rich-content validation and image-upload limits must pass ADR-011's gate before this part of the contract is accepted.

## Live events and recovery

On `GET /v1/events` upgrade, the client sends `subscribe` commands for text channels and the current community presence stream. The server replies with `subscribed` or a stable error. Every live event has `schema_version`, `type`, and `event_id` (opaque UUID). A `chat.message` event contains the full message shape above. A `chat.access_revoked` event contains the affected `community_id` or `channel_id` and `authorization_revision`; the server also stops protected fan-out and closes affected subscriptions. Presence events follow the separate revision rules below.

After reconnect, the client subscribes, buffers incoming chat events, fetches history after its last applied per-channel `seq`, applies history in order, then applies buffered events and deduplicates by `(channel_id, seq)`. A gap triggers another history fetch. A pending send retains its `client_message_id`. A kicked/banned client stops retrying protected operations. A normal network drop retries quickly with backoff and can request a fresh voice admission after full media reconnect.

`GET /v1/communities/{community_id}/presence` returns a `revision`, `members`, and `shares`. A member entry has `user_id`, `display_name`, `online`, `voice_channel_id` or `null`, and confirmed `speaking`, `muted`, and `sharing` flags where known. A share entry has `share_id`, `publisher_id`, `voice_channel_id`, and `track_id`. These identifiers let a client maintain two views and detach one without a second publication. A `presence.delta` event includes `base_revision`, `revision`, and `changes`. The client applies it only when `base_revision` equals its current revision; otherwise it fetches a new snapshot. Online leases and LiveKit observations are ephemeral, so the client can display `reconnecting` or `unknown` while resynchronizing.

```json
{
  "schema_version": 1,
  "type": "presence.delta",
  "event_id": "8ac5ea22-4d03-4b82-8eb2-c39ba13721a2",
  "community_id": "5aee793e-3cde-44fc-9608-48b7e945fb53",
  "base_revision": "71",
  "revision": "72",
  "changes": [{ "kind": "share_started", "share_id": "c9089ac7-a306-464b-8b24-f5900dc0c9b7", "publisher_id": "6daa8a59-0ac7-4737-bdad-768d60607767", "voice_channel_id": "0700eaa6-8204-4f0b-a45e-57d929289818", "track_id": "TR_example" }]
}
```

Voice admission returns the logical `voice_channel_id`, current physical room name, `media_generation`, LiveKit signaling URL, a short-lived room token, and expiry. Only Axum issues this response after checking current authorization. The generation and physical room name exist for Server 006's **Proposed** cutover and must not be treated as proof that old tokens are already enforceably revoked.

## Conformance examples required in Git

The repository includes initial [v1 JSON fixtures](fixtures/v1/) for a message, a two-share roster snapshot, a share-ended delta, and a forbidden error. Each contract owner expands these with machine-readable or documented request/response fixtures for success, malformed input, expired session, forbidden member, kick, ban, and reconnect. Chat adds duplicate send, sequence gap, and revoked subscription. Presence adds lost delta, stale lease, and webhook loss. Media adds expired token, changed room generation, source ending, and normal network resume. Images add invalid format, oversized payload, orphan upload, direct-object denial, and revoked download. Client and server workstreams test against the **same** fixtures before live integration.

No fixture contains a real account, credential, access token, image, screen capture, or private community data. The mock community names are optional disposable sample data and are not required by the protocol.
