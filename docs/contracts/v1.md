# Cordel v1 application contract

**Status:** implementation baseline for Accepted ADRs; browser cookie admission, media revocation, image storage, and E2EE sections remain gated by their Proposed ADRs.

This file is the common input for independent server and client workstreams. Some identity endpoints are deployed and ADR-003 community routes exist in source; other operations remain contract targets behind their ADR gates. The [status ledger](../adr/STATUS.md) distinguishes them. When implementation evidence requires a breaking change, update this file and the affected ADRs in the same reviewed change before changing either side. The [workstream map](../adr/WORKSTREAMS.md) names the owner and consumers of each seam.

## Encoding and compatibility

- Public app calls use HTTPS; live app events use WSS. JSON uses UTF-8 and `snake_case` field names. All timestamps are UTC RFC 3339 strings. IDs are opaque UUID strings; clients do not infer order or permissions from IDs.
- Every JSON response or event includes `schema_version: 1`. Additive optional fields are allowed within v1. Receivers ignore unknown fields and unknown event types. Removing a field, changing its meaning, or changing an error category needs a new schema version and a migration plan.
- Sequence numbers and snapshot revisions are unsigned decimal **strings** in JSON so browsers do not lose integer precision. They are compared numerically, never lexically. Chat sequence is per channel. Presence revision is per community and is not a chat sequence.
- A non-2xx REST response has `{ "schema_version": 1, "error": { "code": "...", "message": "..." } }`. `message` is safe to display but is not a stable programmatic key. Stable codes include `unauthenticated`, `forbidden`, `not_found`, `conflict`, `expired`, `rate_limited`, `invalid_input`, `payload_too_large`, and `temporarily_unavailable`. Do not expose whether a login or invite exists through distinguishable public errors.
- Server configuration owns numeric rate, body, upload, and retention limits. The server returns its effective limit in a validation error where safe. Clients must not assume a documentation example is an unlimited quota.

## Identity and authorization

Native clients send `Authorization: Bearer <app_access_token>` over HTTPS and in the WebSocket upgrade header. The access token is short-lived. The rotating refresh credential is stored only in the OS credential store. The browser path in ADR-009 uses a same-origin `Secure`, `HttpOnly`, `SameSite=Strict` cookie plus CSRF for state-changing requests; it does not place a durable token in a URL or browser JavaScript storage. Browser cookie admission is Proposed until its security gate passes.

For the native ADR-002 identity flow, `POST /v1/accounts/from-invite` accepts `invite_code`, `login`, and `password`. `POST /v1/sessions` accepts `login` and `password`; `POST /v1/sessions/refresh` accepts `refresh_token`. Each successful call returns `schema_version`, `user_id`, `community_id`, `access_token`, `refresh_token`, and `expires_in_secs`. The new refresh token replaces the old one in the OS credential store. Replaying a consumed refresh token revokes its session and requires a new login; there is no retry grace in this first implementation. `DELETE /v1/sessions/current` accepts the current native bearer token, revokes that session, and returns `{ "schema_version": 1 }`. Unknown, expired, exhausted, and login-colliding invites use the same `invalid_input` response. Invalid login credentials use `unauthenticated`. `POST /v1/accounts` returns `public_registration_disabled`. The [identity fixtures](fixtures/v1/) use fixed, unusable credentials for schema checks; never send them to a live server.

`POST /v1/communities/{community_id}/invitations` accepts optional `expires_in_hours` (1–168, default 24) and `max_uses` (1–25, default 1). It returns `schema_version`, `invitation_id`, `invite_code`, `expires_at`, and `max_uses`. The invitation code is shown only in that response, so the admin client must transmit it to the intended invitee through a separate private channel. The code is not recoverable from the database. Under the accepted Management Mode change, this route requires a current admin grant. The previous ADR-002 binary accepted an ordinary admin access token; an authenticated external check confirmed ordinary app-bearer denial and grant-backed issuance with disposable `test-admin`. `GET /v1/me` returns the fields described below and requires the session to remain active. Native access JWTs last 300 seconds; refresh sessions last 30 days. Server 003 owns the reusable policy and future moderation/revocation behavior; the deployed identity routes currently check the minimum membership state in PostgreSQL.

**Accepted Management Mode change:** The grant is installed on the Azure VM and the focused external smoke passed; the dated step-by-step record is in the [ADR-002 evidence](adr/server/ADR-002-invite-only-identity.md). All accounts, including admins, start in ordinary member mode. `POST /v1/sessions/admin-grant` requires the current native app bearer and JSON `{ "password": "<own account password>" }`. Only a current `admin` can succeed. It returns `{ "schema_version": 1, "admin_token": "<opaque secret>", "expires_in_secs": 600 }`. The grant is a random 256-bit value; the server stores only its hash and binds it to the current app session, account, and community. A client keeps it in memory only and sends `Authorization: Bearer <admin_token>` for management operations. Ordinary app access JWTs must fail on those operations even for admins. The server checks the grant, live session, current admin role, and moderation state on each request. `DELETE /v1/sessions/admin-grant` revokes the grant and returns `{ "schema_version": 1 }`. The grant expires after 10 minutes without refresh and is revoked by logout, host password recovery, role removal, kick, ban, or session revocation. Failed unlocks are rate-limited and return the standard error envelope without revealing password details; audit records identify the account and session without containing secrets. A regular user cannot become admin by knowing a shared password; there is no shared `superadmin` credential.

For browser sessions, ADR-009 must bind the same own-password step-up to the live cookie session without exposing an admin bearer to JavaScript. Its unlock, lock, and management requests require the browser CSRF/Origin protections. The diagnostic browser may omit admin controls in its first test, but cookie sessions must not bypass the native management gate.

For the proposed browser path, the browser first calls `GET /v1/browser/csrf` on the application origin. The response carries a CSRF token for JavaScript and a separate pre-login nonce in an `HttpOnly` cookie. The browser sends the token as `X-CSRF-Token` for invite redemption/login and other state-changing requests. Successful login destroys the pre-session and creates a distinct authenticated session and CSRF token; a later same-origin GET to the same endpoint obtains the session-bound value. The endpoint never returns the session secret. The server checks exact Origin and Fetch Metadata when available. Native bearer authentication does not require this browser CSRF flow.

Version one has one community but every community-scoped resource contains `community_id`. `user` and `admin` are the only app roles; Management Mode is a temporary grant, not another role. The host-only admin command has no public endpoint. An admin cannot kick or ban another admin. A kick ends no sooner than 30 minutes after application; a ban has no expiry until an admin lifts it. Every protected read, write, WS subscription, image fetch, and media admission rechecks current membership and moderation state.

The table names interface ownership, not a promise to expose every operation before its ADR gate.

### Minimum resource shapes

`GET /v1/me` returns `user_id`, `login`, `community_id`, `role`, and `session_expires_at`. In the first test, a member's public `display_name` is the registered login; a later profile feature may separate them. The community resource exposes `community_id`, `name`, and `description`. `PATCH /v1/communities/{community_id}` accepts only `name` (1-100 characters) and `description` (at most 1000 characters) from an admin; at least one field is required. DNS, media ports, storage, and host admin assignment are never client-editable. A channel has `channel_id`, `community_id`, `kind` (`text` or `voice`), `name` (1-80 characters), and `created_at`. `POST /v1/communities/{community_id}/members/{member_id}/kick` accepts optional `duration_minutes`, default 30 and no less than 30. A moderation response states `member_id`, `state` (`active`, `kicked`, or `banned`), `kicked_until` when applicable, a new `authorization_revision`, and `media_drained`, which is false when the voice rooms of the previous generation could not be drained and the action is therefore not fully applied. Other endpoints that change access return that revision so consumers can discard stale permissions. The [channel](fixtures/v1/community_channel_created.json) and [kick](fixtures/v1/community_member_kicked.json) fixtures freeze the new response shapes.

`GET /v1/channels/{channel_id}/messages?after_seq=<decimal>&limit=<positive integer>` returns ascending messages newer than the cursor for reconnect catch-up. `before_seq=<decimal>` requests an older page for scrolling history, returned in ascending order. `after_seq` and `before_seq` are mutually exclusive; an omitted cursor requests the most recent page. Responses include `messages` and `has_more` in the selected direction. The server caps `limit`, and never accepts a cursor as proof of access. `POST` takes a client-generated stable `client_message_id` and v1 content. Retrying with the same ID, author, and channel returns the same committed message; reusing the ID for different content fails with `conflict`.

```json
{
  "schema_version": 1,
  "message_id": "418ab662-4882-43bb-9eaf-5ad43261d6a7",
  "client_message_id": "567e491b-4c30-47ec-9fc0-6744c12a6e87",
  "channel_id": "7efc7a7b-b06f-4632-8780-bb611b8cd0a8",
  "author_id": "6daa8a59-0ac7-4737-bdad-768d60607767",
  "seq": "42",
  "created_at": "2026-10-17T12:00:00Z",
  "content": { "format": "cordel_rich_v1", "blocks": [{ "type": "paragraph", "spans": [{ "text": "Hello", "marks": ["bold"] }] }] },
  "images": []
}
```

The rich content and image shapes are **Proposed** under Server 011 and are described in its ADR; the contract accepts them only after that ADR's gate passes. Until then a message carries the ADR-004 body and no image reference.

The image flow is **Proposed** under Server 011: an upload is bound to the authenticated author and channel, the bytes are validated and normalized before an `image_id` exists, an image may be attached to one committed message only, access is rechecked on every step, the download is private and `no-store`, and bytes a client already downloaded cannot be recalled. See the ADR for the limits.

## Live events and recovery

On `GET /v1/events` upgrade, a native client is already authenticated by its bearer handshake header. A browser client sends `{ "schema_version": 1, "type": "browser.authenticate", "csrf_token": "<session-bound value>" }` as its first WS message. Until it validates, the server sends no protected data, accepts no subscriptions, and enforces a short time/byte limit. After a `ready` event, the client sends `subscribe` commands for text channels and the current community presence stream. The server replies with `subscribed` or a stable error. Every live event has `schema_version`, `type`, and `event_id` (opaque UUID). A `chat.message` event contains the full message shape above. A `chat.access_revoked` event contains the affected `community_id` or `channel_id` and `authorization_revision`; the server also stops protected fan-out and closes affected subscriptions. Presence events follow the separate revision rules below. The browser CSRF value is never sent in the URL, a WebSocket subprotocol, or logs.

After reconnect, the client subscribes, buffers incoming chat events, fetches history after its last applied per-channel `seq`, applies history in order, then applies buffered events and deduplicates by `(channel_id, seq)`. A gap triggers another history fetch. A pending send retains its `client_message_id`. A kicked/banned client stops retrying protected operations. A normal network drop retries quickly with backoff and can request a fresh voice admission after full media reconnect.

`GET /v1/communities/{community_id}/presence` returns a `stream_id`, `revision`, `members`, and `shares`. `stream_id` is an opaque UUID for one Axum presence-state epoch and changes after state rebuild or process restart; revision increases only within that epoch. A member entry has `user_id`, `display_name`, `online`, `voice_channel_id` or `null`, and confirmed `sharing` where known. A share entry has `share_id`, `publisher_id`, `voice_channel_id`, and `track_id`. These identifiers let a client maintain two views and detach one without a second publication. A `presence.delta` event includes the same `stream_id`, `base_revision`, `revision`, and `changes`. The client applies it only when `stream_id` and `base_revision` match its current snapshot; otherwise it fetches a new snapshot. Online leases and LiveKit observations are ephemeral, so the client can display `reconnecting` or `unknown` while resynchronizing. Speaking and microphone-mute indicators come from the connected client's LiveKit room/track events.

For a race-free initial roster, subscribe to the presence stream and buffer its deltas, fetch the HTTP snapshot, then apply only buffered deltas whose `stream_id` and `base_revision` match. Refetch on a gap or epoch change. A member is online when an authorized app WS lease **or** authorized LiveKit participation is live; a valid refresh session alone does not mean online.

```json
{
  "schema_version": 1,
  "type": "presence.delta",
  "event_id": "8ac5ea22-4d03-4b82-8eb2-c39ba13721a2",
  "community_id": "5aee793e-3cde-44fc-9608-48b7e945fb53",
  "stream_id": "448aa588-0e69-4453-a03e-138664dcaac6",
  "base_revision": "71",
  "revision": "72",
  "changes": [{ "kind": "share_started", "share_id": "c9089ac7-a306-464b-8b24-f5900dc0c9b7", "publisher_id": "6daa8a59-0ac7-4737-bdad-768d60607767", "voice_channel_id": "0700eaa6-8204-4f0b-a45e-57d929289818", "track_id": "TR_example" }]
}
```

Native frames use `v: 1` and `kind: presence.delta`; `presence.resync` means refetch. Subscribe with `{ "v": 1, "kind": "subscribe", "presence": true }`. Kinds: `member_online`, `member_offline`, `voice_joined`, `voice_left`, `share_started`, `share_ended`. A dropped socket stays online for 90 seconds; a kick or ban removes the member.

Voice admission returns the logical `voice_channel_id`, current physical room name, `media_generation`, LiveKit signaling URL, a short-lived room token, and expiry. Only Axum issues this response after checking current authorization. The generation and physical room name exist for Server 006's **Proposed** cutover and must not be treated as proof that old tokens are already enforceably revoked.

The implemented response is `{ "schema_version": 1, "voice_channel_id": "<uuid>", "room": "voice:<channel-uuid>:<generation>", "media_generation": 0, "url": "<signaling url>", "token": "<room token>", "expires_at": "<rfc3339>", "expires_in_secs": 300 }`. The `media_generation` is the community's current `authorization_revision`, which advances when a moderation action is applied, so an admission minted before the action names a room that is no longer current. The room token is a LiveKit JWT scoped to one account and one room: it may join, publish, and subscribe, and it may not publish data tracks, create rooms, or administer them. Chat therefore never rides a LiveKit data track. The token lives 300 seconds, which matches the app access token; LiveKit checks it when a participant joins, not during a call, so a client that must rejoin asks for a fresh admission.

## Conformance examples required in Git

The repository includes initial [v1 JSON fixtures](fixtures/v1/) for a message, a two-share roster snapshot, a share-ended delta, and a forbidden error. Each contract owner expands these with machine-readable or documented request/response fixtures for success, malformed input, expired session, forbidden member, kick, ban, and reconnect. Chat adds duplicate send, sequence gap, and revoked subscription. Presence adds the lost-delta fixture `presence_gap_delta.json`; stale-lease and webhook-loss behavior are covered by the identity unit tests. Media adds expired token, changed room generation, source ending, and normal network resume. Images add invalid format, oversized payload, orphan upload, direct-object denial, and revoked download. Client and server workstreams test against the **same** fixtures before live integration.

No fixture contains a real account, credential, access token, image, screen capture, or private community data. The mock community names are optional disposable sample data and are not required by the protocol.
