**Local two-client chat proof (2026-10-21):** `deploy/native/local-lxc-e2e.sh` runs the ADR-004 chat path end to end on the disposable LXC: a fresh database, migrations, the first admin, the Axum server on loopback, a text channel and a second member created through the public API, then the opt-in Phase 0 chat tests and a check that the Phase 0 window opens with the chat surface. The run passed. `two_clients_exchange_messages_over_the_live_session` proves the missing two-client case: the second client posts through the same REST route the native client uses and the first client receives it on the live socket, then the first client sends and the second client reads the committed message from history. This is local evidence for Server 004 and Client 102. It is not the two-network proof the ADRs ask for, and it is not deployed.

**Media admission gate (2026-10-21):** The Server 005 token and the Server 006 gate are implemented. The gate answers the reverse proxy on a second loopback listener and refuses a token whose room names a stale generation, whose account is not an active member, or whose app session is no longer live; the admission token carries that session. A moderation action deletes the rooms of the previous generation through the LiveKit server API, and the moderation response reports whether the drain happened. On the disposable LXC a real Caddy reverse proxy proved it end to end: a client joined through the proxy with a valid admission, a moderation action advanced the generation and drained the room, and the same token was refused with 403 through the same proxy. The LiveKit SDK sends the token in the `Authorization` header, so the gate reads the bearer the proxy copies. The Caddy change is written in the deployment runbook and is not applied to a deployed host.

**LiveKit local measurement (2026-10-21):** A disposable local `livekit/livekit-server:v1.13.10` was measured before the Server 005 design was settled; the findings and the reproduction are in the [LiveKit local spike](../spikes/livekit-local-2026-10-21.md) and `deploy/native/local-livekit-probe.sh`. The API secret needs at least 32 characters, a participant token is a plain HS256 JWT with a minimum `video` grant, a webhook arrives as a JWT in the `Authorization` header whose `sha256` claim pins the raw body, and the server API needs a room-scoped admin JWT. Axum can remove a participant from a room, but a held token rejoins and republishes after `RemoveParticipant` and `DeleteRoom` both succeeded, so the gap is total on self-hosted LiveKit and the isolation proof cannot succeed. That is why the gate exists. No Azure and no production resource was involved.

## Definition of done for one ADR

Mark an ADR `Done` only when all applicable items are true:

1. Its design is Accepted. For a Proposed ADR, first resolve the explicit acceptance gate with the project owner and record the result in that ADR; do not relabel it from an agent's assumption.
2. Its owned implementation or deliverable is complete in the repository. A feasibility ADR may close with a documented negative result and a superseding ADR, but it is not `Done` while its required solution is missing.
3. Its side of the [v1 contract](../contracts/v1.md) has versioned fixtures or schemas, the consuming workstream has reviewed the shared seam, and conformance checks pass.
4. Its own verification section has reproducible evidence: commands and output for code checks, disposable test setup, real OS/network measurements where required, and clearly stated limits.
5. Cross-workstream failures attributable to it are fixed or explicitly recorded as a blocking open item. Its documentation and this ledger match the implementation.

GitHub Issues are filed manually by people. Agents fix issues discovered during authorized work and rerun the affected checks. If a fix cannot be completed within the task, keep the ADR In progress, record the open gate here with sanitized evidence, and tell the owner; do not open a GitHub Issue automatically. Link an existing human-filed issue from the affected ADR row or deployment record when relevant. Verify a fix before proposing that an existing issue be closed.

Technical spikes, unit tests, contract checks, security proofs, and isolated integration checks are **part of completing ADRs** and may run before product testing. A user-facing integrated product test starts only when **all 16 first-test mandatory ADRs** below are `Done`. The later roadmap ADRs do not block that first test. They gate their own platform or final-release claims.
